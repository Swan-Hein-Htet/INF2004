Priority and ownership justification:
The order comes from deadlines, not from importance, with one deliberate exception for safety.
Rate-monotonic baseline. The shorter the period, the higher the priority. T2 LineBarcode has the shortest (1
ms), because the barcode decoder must resolve a 3 mm narrow element that lasts only 15 ms at the clamped
traverse speed. T3 follows at 10 ms, then T4 at 20 ms, then T5 (70 ms ping cycle) and T6 (event-driven) by
response budget, and last the network task, which has no hard deadline.
The one exception. T1 SafetyMonitor has a 20 ms period, so rate-monotonic ordering would put it alongside T4.
It is given priority 4 instead, above everything. A decision to cut the motors is only useful if it reaches them
before the next ordinary speed command does; at T4's priority, T1 could sit ready while T2 and T3 run and the
motors would take one more PID update first. The cost is bounded: T1's worst case is about 150 µs, so it
delays T2 by at most 150 µs out of a 1 ms period that has roughly 940 µs of slack.
Worst-case utilisation. These are estimates and will be replaced with measurements after Week 6:
   T2 LineBarcode      period 1 ms    WCET 60 µs               U = 6.00%
    T3 ImuTerrain      period 10 ms   WCET 700 µs              U = 7.00%
    T4 MotionCtrl      period 20 ms   WCET 300 µs              U = 1.50%
    T1 SafetyMonitor   period 20 ms   WCET 150 µs              U = 0.75%
    T6 VehicleCtrl     min. 50 ms     WCET 250 µs              U = 0.50%
    T7 Telemetry       period 200 ms WCET 6.0 ms               U = 3.00%
    T5 ObstacleScan    period 70 ms   WCET 100 µs              U = 0.14%
    Encoder + echo ISRs ~130 events/s   WCET   3 µs            U = 0.04%
                                                              Total ≈ 18.9%

T5 ObstacleScan is included: O0 WATCH pings every 70 ms for the whole run, not only while the vehicle is
halted, so it is a periodic task. Its 100 µs WCET is an estimate (trigger pulse plus range arithmetic). The Liu and
Layland sufficient bound for seven periodic tasks is 7(2^(1/7) − 1) ≈ 72.9%, so at roughly 19% the task set is
comfortably schedulable with the margin NFR15 requires. The least certain figure is T3's I²C burst: 14 bytes at
400 kHz is about 375 µs of bus time, charged to the CPU if the driver busy-waits. That is why T3 sits below T2.
Blocking and ownership. mtx_state is the only mutex in the design. It is created with TA_INHERIT, so a low-
priority task holding it is temporarily raised to the priority of whoever is waiting, and no task holds it for more
than about 100 µs — the rule is to copy what you need out, release, then do the work. Nothing else needs a
lock, because every other shared resource has exactly one owning task: T2 owns the three ADC channels, T3
owns I²C0, T4 owns the motor PWM, T5 owns the servo, T7 owns the network. Single ownership was chosen
over adding mutexes because an uncontended mutex is still code that has to be understood and defended.

Brief explanation of the main communication paths:
Figure 2 reads top to bottom: hardware, interrupt handlers, sensing tasks, kernel objects, the mission task, and
then the acting tasks and their hardware. Following it downwards traces one sensor reading through to a motor
command.
The design uses only three kinds of μT-Kernel object, which keeps the number of mechanisms the team has to
understand and defend small:
   message buffer (a queue)   mbf_nav, mbf_motion
    event flag (an event group) flg_sys
    mutex                      mtx_state

Two queues carry work. mbf_nav carries a decoded navigation command from T2 to T6. mbf_motion carries a
motion request from T6 to T4. While the mission is in S7 OBSTACLE_HANDLE, T5 posts its own motion
requests to mbf_motion and T6 posts none, so T4 only ever has one sender at a time. Both are message
buffers rather than mailboxes, which means the kernel copies the small request structure and no task has to
think about who owns a pointer or when to free it. An earlier version of this design used a mailbox of pointers
and a fixed-size memory pool for the obstacle profile; both were removed once the team worked out that an
obstacle profile is only about a dozen bytes, so copying it costs nothing and a memory pool buys nothing.
One event flag carries conditions. LINE_LOST, OBSTACLE, HUMP, NET_UP, ESTOP, START and
MOTION_DONE are states of the world, not messages with a payload, and T6 needs to wake on whichever
happens first. tk_wai_flg with TWF_ORW does exactly that. A queue here would have forced T6 to drain and
re-dispatch messages it did not care about. MOTION_DONE (B6) is set by T4 when a manoeuvre completes;
the task that posted the request (T6, or T5 during S7) waits for it and clears it. This replaces a separate DONE
reply, so no new kernel object is needed.
One mutex protects the one genuinely shared thing. g_vehicle_state is a single structure holding speed,
distance, line error, pitch, hump height, the obstacle profile and the system state. Several tasks write parts of it
and T7 reads all of it. The rule every task follows is the same: take the lock, copy, release, then do the work
outside the lock.
Interrupts stay short. The two encoder ISRs increment a count. The echo ISR records the pulse width and calls
tk_wup_tsk on the falling edge only, so T5 is woken once per ping. None of them does arithmetic, and none
takes longer than about 3 µs. Everything else is done in a task.
Actuation has one owner each. T4 is the only task that writes the motor PWM registers and T5 is the only one
that moves the servo. There is exactly one documented exception, drawn in red: T1 SafetyMonitor writes the
motor registers directly to force them off. This deliberately breaks single ownership, because the safe state
must not depend on T4 being schedulable — if T4 has blocked or faulted, routing the shutdown through it
defeats the purpose. T4 notices on its next release that its outputs were overridden and resets its PID
integrators instead of fighting the override.
Telemetry cannot stall the robot. T7 takes the lock, copies the state, releases the lock, and only then formats
and publishes. It runs at the lowest priority of any task. So a slow broker, a lost access point or a blocked
socket costs stale telemetry and nothing else; no control loop can be delayed by the network.

Explain the main states and any important assumptions:
Figure 3 is the mission state machine, held entirely inside T6 VehicleCtrl: one task owns the state variable,
waits for one event at a time, dispatches, acts briefly and returns to waiting. No other task changes the system
state, and T6 never blocks inside a transition action — a manoeuvre is started by posting a request to T4, and
its completion arrives later as a separate event.
From S3 LINE_FOLLOW the machine branches to whichever mission feature fires first: a barcode quiet zone to
S4 and then S5, a pitch excursion to S6, an ultrasonic return under 200 mm to the composite state S7. All three
return to S3. While S7 is active, T5 drives the bypass through mbf_motion and T6 posts no motion requests. S7
exits on LINE_REACQUIRED to S3, or on BYPASS_FAILED (a second blocked attempt, with flg_sys ESTOP
set) to S10. While in S7, T6 ignores and does not clear MOTION_DONE or LINE_LOST: during S7 only T5
clears MOTION_DONE, and T2 clears LINE_LOST as soon as it sees the line again, before T5 raises
LINE_REACQUIRED. This gives each flag exactly one owner during the bypass.
Speed is a property of the state, not a global setting. S3 runs at a nominal 250 mm/s, S4 clamps to 200 mm/s
so the barcode sampling margin in NFR1 holds, and S6 clamps to 150 mm/s so the pitch estimate is not
swamped by suspension bounce. S7 runs its O6 and O7 bypass legs at 250 mm/s and creeps at 120 mm/s in
O8 and O9. Making the limit part of the state rather than a variable several tasks may write means it can be
read off the diagram and tested per state.
Rejection is a first-class outcome. S4 → S3 on BARCODE_REJECT exists because guessing a command from
a partial read is the most damaging failure this robot has available to it. A missed barcode costs one junction; a
wrongly decoded one sends the vehicle off the course. FR6 and NFR9 state this as a requirement and the chart
implements it.
Fault handling. The global fault triggers are listed once on the figure rather than drawn from every state. Any of
them sends the system to S10, and only an explicit RESET with the condition cleared returns it to S2, which re-
runs the self-test. Note that T1 SafetyMonitor forces the motor PWM off as soon as it sees the condition,
without waiting for T6 to be scheduled; T6 then observes flg_sys BIT0 and moves the mission state to S10. The
state machine records the fault it is not what makes the vehicle safe.
Two assumptions this chart carries. The end of the course is assumed to be marked by a sustained all-black
reading; if the real course has no such marker, S9 will be entered by MQTT command instead and the
END_MARKER transition removed. The 8 s timeout on S8 is a placeholder, chosen to exceed the worst bench-
test recovery, and will be re-tuned against the real course.

6.1 Line Following and Barcode Decoding
 Field                      Student Entry

 Subsystem name             Line Following and Barcode Decoding

 Related RTOS task(s)       T2 LineBarcode

                            Turn three raw IR channels into (a) a continuously updated signed line error for the
 Purpose                    motion controller and (b) discrete, validated navigation commands decoded from
                            Code 39 barcodes beside the line.

                            The subsystem has two behaviours that must not interfere: a continuous tracking
                            loop and a one-shot capture-and-decode sequence with a strict element budget and
 Reason a statechart is     a timeout. The decode sequence has a clear start condition (a quiet zone), an
 needed                     accumulation phase, a validation step and two distinct exits. Flags alone would not
                            make the mutually exclusive capture phases explicit, and a wrongly re-entered
                            capture would corrupt a symbol mid-read.




                   Figure 4 — Subsystem statechart: Line Following and Barcode Decoding (T2, Buddy 3)

Brief explanation of states, events, and fault handling:
L0 CALIBRATE runs once per session, started by T6 during S1, for a 3-second sweep duration: the vehicle is
swept across the line (and the sweep must pass the barcode sensor over a black bar). The minimum and
maximum of each channel are recorded, the threshold is set midway, and the span stored so the error can be
normalised. If the computed span is below a minimum threshold, it follows a failure path to retry. This is what
makes NFR10 achievable — an absolute threshold would fail the moment the room lighting changed.
L1 TRACK is the steady state. T2 runs every 1 ms, reads the three ADC channels itself — three conversions is
about 6 µs — and recomputes e = (adcL − adcR)/span and republishes every 10 ms (NFR2). The two
degenerate readings get their own states rather than flags: L2 JUNCTION and L3 LOST. L3 sets flg_sys
LINE_LOST, which is what moves the mission machine into S8.
The barcode branch is armed from L1, not from a timer. Line tracking (L1–L3) continues throughout capture.
Capture aborts without a command if the line leaves L1. B0 QUIET_ZONE requires the barcode channel to be
clear for at least 10 mm of travel, so a stray mark cannot start a capture. B1 CAPTURE then timestamps every
transition, exiting on either 29 elements — three Code 39 characters at nine elements each, plus two inter-
character gaps — or when no edge arrives for 300 ms, so a truncated symbol never leaves the task waiting.
The symbol takes 705 ms at 200 mm/s, so 300 ms can’t be a total limit.
B2 DECODE holds the key decision. Captured durations are divided by the median of the shortest third of the
elements, giving a dimensionless ratio per element. The rule is: narrow below 0.5× reference is rejected, wide
above 4× is rejected, and 2.0× is the narrow/wide boundary. Because classification is on ratios, the decode is
unaffected by the vehicle accelerating mid-symbol, which is what NFR8 requires and an absolute-time decoder
could not deliver.
The symbol geometry was derived, not assumed. For Code 39 at a 1:3 ratio one character spans six narrow
plus three wide elements, i.e. 15 narrow units; the delimited symbol *X* is three characters plus two inter-
character gaps, i.e. 47 narrow units. The supplied specification gives 141 mm, so one narrow unit is 3 mm and
one wide unit is 9 mm. At the clamped 200 mm/s a narrow element lasts 15 ms, so 1 kHz sampling yields about
15 samples per element — comfortably above the 10 needed to resolve a width to 10%.
B4 REJECT is the explicit failure exit and returns to L1 without emitting a command, logging the reason —
element count, start/stop mismatch, or ratio out of range — to telemetry, so a poor read can be told apart from a
missed barcode during testing. The subsystem never emits a command it is not certain of.

6.2 Motion Control
 Field                    Student Entry

 Subsystem name           Motion Control

 Related RTOS task(s)     T4 MotionCtrl, with ISR_ENC_L and ISR_ENC_R

                          Provide stable, repeatable, closed-loop motion and a non-blocking motion API
                          (moveForward, moveBackward, turnLeft, turnRight, setSpeed, stop) to the rest of the
 Purpose
                          system, and maintain the odometry that the terrain and obstacle subsystems depend
                          on.

                          The same task has to serve two incompatible kinds of command: a continuous
                          speed-tracking mode driven by the line error, and discrete goal-seeking manoeuvres
 Reason a statechart is
 needed
                          that must finish and report completion. It also has to arm and disarm safely and fail
                          cleanly on a stall. Writing that as flags inside one control loop produces exactly the
                          tangle of conditions the statechart lecture warns against.
                            Figure 5 — Subsystem statechart: Motion Control (T4, Buddy 2)

Brief explanation of states, events, and fault handling:
M0 DISARMED is the power-on and post-fault state: both PWM channels at zero, H-bridge coasting rather than
braking. M1 ARMED_IDLE holds a zero setpoint with the PID integrators pinned at zero, so arming never
produces a kick from stored error.
Three command states branch from M1. M2 DRIVE is the continuous mode used while line following: an outer
loop turns the line error into a difference between the two wheel setpoints, and an inner per-wheel PID tracks
them every 20 ms with a clamped integrator. M3 TURN and M4 MOVE_DIST are goal-seeking, each working
out a target in encoder counts. M5 RAMP_DOWN has its own state because stopping abruptly at the goal
overshoots on a light chassis, and because the ramp must stay interruptible by a fault. M6 HOLD brakes for 100
ms, coasts, and reports completion to T6 — completion is an event, never an assumption about elapsed time.
How speed is measured. The two ISRs do nothing but increment a counter. Every 20 ms T4 reads and clears
them and keeps the last five readings, so speed is the edge count over the most recent 100 ms. The averaging
window is deliberately longer than the control period, for a reason worth stating because it otherwise looks like
a mistake.
One encoder edge is about 5.1 mm of travel (20 slots, two edges per slot, 65 mm wheel). At the nominal 250
mm/s the vehicle covers only about 5 mm per 20 ms tick, so counting edges within one tick gives one edge,
sometimes zero — a speed estimate quantised to roughly ±100%, and a PID tuned against quantisation noise
rather than the wheel. Averaging over 100 ms gives about five edges and roughly ±20%, at the cost of up to
100 ms of lag. That is acceptable here because the loop that has to be quick is steering, which runs off the line
error, not off speed. If bench testing shows ±20% is not enough, the fallback is to timestamp each edge and
compute speed from the gap between them; that is more code to write and defend, so it is held as a refinement.
Edge counts also give distance, where the same quantisation is 0.26% over 2 m, inside NFR11. The slot count
and wheel diameter must be measured, not taken from the kit datasheet — assumption A2.
M7 STALL_FAULT is entered when commanded duty exceeds 60% while measured speed stays below 20
mm/s for 500 ms, which is what a blocked wheel or a detached encoder looks like. The self-transition on M0
records that T1 can force the outputs off from any state; T4 treats that as an external event and resets its
integrators rather than reasserting control.

6.3 IMU Motion and Terrain Monitoring
 Field                    Student Entry

 Subsystem name           IMU Motion and Terrain Monitoring
 Related RTOS task(s)      T3 ImuTerrain

                           Maintain a filtered pitch estimate, classify the vehicle's motion, detect the start and
 Purpose                   end of a hump, estimate its height, and report the maximum peak height for the run.
                           Also detect impacts.

                           Hump traversal is a sequence of phases — ascent, crest, descent — that can only be
                           distinguished by the order in which pitch thresholds are crossed, not by the
 Reason a statechart is
 needed
                           instantaneous pitch value alone. A single pitch reading of 0° means something
                           entirely different on the crest of a hump than it does on flat ground, which is the
                           defining signal that an explicit state is needed.




                    Figure 6 — Subsystem statechart: IMU Motion and Terrain Monitoring (T3, Buddy 4)

Brief explanation of states, events, and fault handling:
I0 INIT verifies WHO_AM_I and configures the MPU-6050 with an accelerometer full-scale range of ±8 g and
the low-pass filter setting specified in NFR4;
I1 BIAS_CALIBRATE requires the vehicle to remain stationary for two seconds. It averages the gyroscope
readings on each axis to estimate gyro bias and subtracts these offsets from subsequent gyroscope readings. It
uses the stationary accelerometer vector to establish the gravity-referenced flat-ground pitch and roll baseline.
The entire stationary accelerometer average must not be subtracted as bias because it contains the gravity
measurement. The installed sensor-axis orientation and positive-pitch convention must be verified.If the vehicle
moves or the calibration readings are unstable, calibration fails and the vehicle remains disarmed. T3 reports
IMU_FAULT to T1 SafetyMonitor. During operation, three consecutive I²C read timeouts also raise IMU_FAULT
and request the system-level safe state S10. The fault is considered cleared only after sensor communication is
restored and the sensor self-test passes. An explicit RESET must then be accepted before the vehicle can start
another run.
I2 FLAT runs the complementary filter θ = 0.98(θ + ωΔt) + 0.02·θ_accel, using the gyro for short-term response
and gravity for long-term reference. The 0.98 weight gives a time constant of about 0.5 s at 100 Hz — long
enough to ignore motor vibration, short enough to track a hump.
The hump sequence is I3 ASCEND, I4 CREST, I5 DESCEND, I6 REPORT. Three consecutive samples above
+6° are required to enter I3, which rejects single-sample spikes from wheels crossing a seam. I4 exists
specifically because the crest is a flat reading in the middle of a hump; without it the machine would fall back to
I2 at the top of every hump and lose the accumulated height. A sharp hump with no measurable crest is
handled by the direct I3 → I5 transition.
Let θ_rel be the filtered pitch relative to the calibrated flat-ground reference, and let Δd_k be the forward
distance travelled during sample k. At the start of each detected hump, the subsystem resets the current
relative-height accumulator h_current to zero and initialises the per-hump peak h_peak to zero. At every 10 ms
sample, it updates h_current = h_current + sin(θ_rel,k) × Δd_k and h_peak = max(h_peak, h_current). The
peak is retained throughout descent, even when the accumulated relative height decreases.
When the hump traversal finishes, T3 reports the measured peak for that hump and updates the maximum
peak height recorded for the run. The run-wide maximum is not reset when a new hump begins. This
calculation depends on the calibrated pitch estimate and reliable encoder distance; therefore, wheel slip, pitch-
reference error and filter lag must be evaluated during testing against NFR13's ±5 mm accuracy requirement.
The cost is a hard dependency on Buddy 2's distance measurement, recorded as assumption A6. It is why T3
and T4 both touch g_vehicle_state, and why wheel slip on the hump face degrades the height estimate. The
team accepted the trade because a first-order error proportional to a measurable quantity is far easier to bound
and test than an unbounded second-order drift.
I7 IMPACT is entered when the accelerometer-vector magnitude exceeds 3 g for two consecutive 10 ms
samples. T3 raises an IMPACT motion event and sets flg_sys IMPACT when the event meets the defined
critical-impact criterion. T1 SafetyMonitor then forces the motor outputs off and requests the system-level safe
state S10. The vehicle remains stopped until the fault condition has cleared and an explicit RESET is accepted.

 Purpose
                          does not touch it, and hand control back once the line has been reacquired.

                          This is the longest sequential behaviour in the system: twelve phases, several taking
                          hundreds of milliseconds, which must not be re-entered, plus two failure exits and a

                          retry. It is also the subsystem most likely to be interrupted midway by a fault, so
                          every phase needs a defined abort behaviour. A statechart is the only practical way
                          to keep it reviewable.
         Figure 7 — Subsystem statechart: Adaptive Ultrasonic Scanning and Obstacle Avoidance (T5, Buddy 5)

Brief explanation of states, events, and fault handling:
O0 WATCH is where the subsystem spends most of a run: servo centred, one forward ping every 70 ms. A
return under 200 mm moves to O1 HALT, which posts stop() to mbf_motion and waits for flg_sys
MOTION_DONE. Scanning never starts while the vehicle is still moving, because a scan taken during
deceleration confuses bearing with distance travelled. The brief suggests slowing near an obstacle; this design
halts instead. The 200 mm trigger is checked every 70 ms, in which the vehicle moves at most 17.5 mm at 250
mm/s, and no scan starts until the stop is confirmed. The stopping distance from 250 mm/s will be measured in
the A5 bench test.
The scan is adaptive, in two stages, which is what the subsystem is named for. O2 COARSE_SCAN sweeps
five angles — 30, 60, 90, 120 and 150 degrees — allowing the servo 50 ms per 30° of travel to settle (100 ms
for the first 60° move from centre) and 70 ms for the ping at each, about 650 ms in total. O2 passes to O3 only
if some coarse return is under 400 mm, twice the 200 mm trigger, so a distant wall does not start a fine scan.
O3 FINE_SCAN then samples seven angles at 10 degree spacing around the nearest coarse return, starting
from whichever end is nearer the servo's current position, a further 940 ms in the worst case. The coarse pass
answers "is something there and roughly where"; the fine pass is what makes the width and clearance figures in
FR17 trustworthy enough to plan a bypass from.
The 70 ms gap between pings is not slack: the HC-SR04 datasheet recommends a measurement cycle of over
60 ms so the previous burst cannot be read as a new echo, and 70 ms gives 10 ms of margin. The settle time
scales with the size of each servo move. 50 ms per 30° is the team's working figure for the SG90, which the kit
documentation does not specify, so it is validated under assumption A9 (Note: Keep this A9, but add A9 "SG90
servo settling time" to Section 7).. Together they set the roughly 1.6 s the vehicle spends stationary.
A coarse scan that finds nothing returns straight to O0 without a fine pass. Without that path a single spurious
return would commit the vehicle to a 1.6 s stop and a bypass it does not need.
O4 PROFILE reduces the fine scan to a location, a width, the closest point and the clearance of each side,
written into the shared state under mtx_state. The HC-SR04 datasheet gives a 15° measuring angle, so each
edge is detected about 7.5° before the beam centre reaches it. O4 therefore subtracts 2·d·tan 7.5° (about 0.26
× d, roughly 53 mm at d = 200 mm, where d is the closest-point range) from the raw width. The front-facing
sensor cannot see the obstacle's depth, so depth is taken as equal to width (assumption A10). The profile is
about a dozen bytes, so it is simply copied — there is no memory pool and no pointer ownership to reason
about. O5 PLAN then chooses between continuing, going left, going right, or reversing and reattempting. It
continues (back to O0) when the profiled obstacle lies outside the robot's path, meaning its near edge is more
than B/2 + 50 mm from the line centre (B = robot width). Otherwise it takes the side with more clearance, as the
brief requires, provided that side has at least B + 100 mm; if the two clearances are within 20 mm of each other
it takes the left side, so the choice is repeatable. If neither side qualifies it goes to O10, whose first-attempt path
is the reverse-and-reattempt option.
The bypass is three explicit legs — O6 out, O7 along, O8 back in — rather than one computed curve, because
three encoder-goal manoeuvres can each be tested on their own against Buddy 2's motion API. O6 turns 60°
away and drives S / sin 60°, where S = W/2 + B/2 + 50 mm and W is the corrected width, so the sideways shift
always leaves the 50 mm clearance of NFR14 whatever the obstacle's size. O7 turns back and drives W + L +
100 mm (L = robot length, with 50 mm of clearance before and after the assumed depth). O8 turns 60° toward
the line. B = [measured robot width] mm and L = [measured robot length] mm are still to be measured on the
assembled car. O6 and O7 run at 250 mm/s; O8 and O9 creep at 120 mm/s. Time budget (NFR23): the two
scan passes take about 1.6 s, so band A (under 3 s) is out of reach, and band B (under 5 s) depends on B and
L; leg speeds will be tuned against NFR23 once they are measured.
O9 REACQUIRE creeps at 120 mm/s until the IR channels see black, falling back to a ±45° sweep, then raises
LINE_REACQUIRED, re-centres the servo and returns to O0, handing control back to the line-following
behaviour. O10 BLOCKED is entered when no side has at least B + 100 mm of clearance, or the line is not
found within 400 mm. On the first failure O11 reverses 120 mm and retries one coarse scan, which recovers the
common case of having stopped too close to see around the obstacle. A second failure sets flg_sys ESTOP
and leaves S7 through BYPASS_FAILED, so the mission moves to S10 and the vehicle stays stopped until
RESET, because an obstacle the vehicle cannot pass is something the operator should see.
Abort. On every release T5 reads flg_sys with tk_ref_flg. If ESTOP is set, it abandons the current phase, posts
no further motion requests, centres the servo to 90° and returns to O0 once RESET clears the fault. T1 has
already forced the motors off, so T5 does not need to stop them itself.
Self-test. In S0 INIT, T5 centres the servo and fires one ping; a complete echo pulse must arrive within 70 ms,
or POST_FAIL is raised. This is how FR25 and IT-25 cover the ultrasonic sensor.

 Field                     Student Entry

 Subsystem name            WiFi / MQTT Link and Telemetry

 Related RTOS task(s)      T7 Telemetry

                           Maintain the WiFi association and MQTT session, publish telemetry at 5 Hz, accept
 Purpose                   START, STOP and RESET commands, and recover automatically from any
                           disconnection without disturbing navigation.

                           Connectivity is a lifecycle with several failure points, each of which has a different
                           recovery: an association failure must retry the join, a broker refusal must retry only
 Reason a statechart is    the connect, and repeated failure must stop retrying rather than spin. Backoff state
 needed                    and retry counts have to persist across attempts. This is the textbook case for an
                           explicit link state machine, and it maps directly onto the RTOS FSM pattern from the
                           lecture — one task, one state variable, events from a queue.
                   Figure 8 — Subsystem statechart: WiFi / MQTT Link and Telemetry (T7, Buddy 1)

Brief explanation of states, events, and fault handling:
N0 DOWN through N4 ONLINE is the normal bring-up: initialise cyw43_arch, join the access point, get a DHCP
lease, open the MQTT session with a keepalive and a last-will message, subscribe to the command topic and
start publishing telemetry.
The QoS split is deliberate. Telemetry is a stream where the newest sample replaces the last, so at-most-once
delivery is right and retransmitting stale samples would be unhelpful. Commands are one-shot and must not be
lost, so they are taken at least once, and the handler is idempotent because at-least-once permits duplicates.
N5 BACKOFF is one state shared by every failure, holding the attempt count and current delay, with jitter so
several robots in the same laboratory do not retry in step. It returns to N1 or N3 depending on whether the WiFi
link itself survived, since reconnecting a broker session does not require rejoining the network. After ten
consecutive failures N6 DEGRADED pauses retries for a minute, so a mistyped network name shows as a
visible symptom rather than a silent loop.
One task, not two. An earlier version split this into a formatting task and a network task with a queue between
them. They were merged: the single task takes the lock, copies the state, releases it, and only then formats and
publishes — so the network work already happens outside the lock, which is what the split was there to
guarantee. Merging removed a task, a queue and a queue policy without weakening anything.
Assumption A1 shaped the rest. lwIP and the cyw43 driver are not re-entrant, and unlike FreeRTOS there is no
published lwIP port for μT-Kernel 3.0. The team therefore uses pico_cyw43_arch_lwip_poll and keeps every
network call inside T7. This is stricter than a mutex and chosen over one deliberately: a mutex would make
concurrent calls mutually exclusive but not safe, because the stack's own timers and callbacks run from
whichever context polls it.
T7 runs at priority 20, below every control task, and nothing waits on it. There is therefore no path from a
network stall back into a control loop, which makes NFR19 a property of the structure rather than a hope. Loss
of the link is not a vehicle fault: the robot must finish the course with no network at all.

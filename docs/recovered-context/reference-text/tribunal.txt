NEW — fault mask (g_faults, uint8_t)
Written by T3, T4, T5, T7 and ISR_BTN; read by T1, T6, T7
T1 SafetyMonitor (Buddy 4) owns the policy; the byte itself has no single writer
Bit set/clear, read-modify-write from both tasks and an ISR
The RP2040 (Cortex-M0+) has no atomic read-modify-write, so an unprotected |= from a task can lose a bit set by an ISR between its load and its store.
All access through fault_set() / fault_clear() helpers that mask interrupts for the load-OR-store (a few cycles, well inside NFR16). Readers do one aligned byte load, which is atomic. A separate compile-time FAULT_CRITICAL_MASK excludes WiFi loss so NFR19 still holds.
Stress test: drive all four interrupt sources while three tasks set and clear bits; assert no set bit is ever lost and no cleared bit reappears.
NEW — packed single-writer words (line word, echo word, encoder counters)
Line word: written T2, read T4/T6/T7. Echo word: written ISR_ECHO, read T5. Encoder counters: written by each encoder ISR, read T4.
The single writer named per variable
One aligned store by the writer; one aligned load by each reader
A word packing several fields is corrupted if two writers do read-modify-write on it; a reader can also see a half-updated value if the compiler splits the access.
Exactly one writer per word; volatile with a static assertion on size and alignment; encoder counters are free-running (the ISR only increments, T4 subtracts the previous value) so no clear-race exists. Requires the NFR20 amendment below.
_Static_assert output in the build log, plus the stress test above; code review confirming one writer per listed variable.

A1
lwIP and cyw43 can be used safely under μT-Kernel 3.0 provided every network call is made from a single task (T7) using the polling cyw43_arch variant.
Open / Needs validation
None on hardware. Supported only by the Week 6 reasoning and the single-owner rule in Figure 2.
A blocking poll call overruns T7’s 200 ms period; worse, silent corruption of lwIP state showing as random freezes after a long run. Largest redesign cost in the document.
Standalone WiFi/MQTT image publishing at 5 Hz for one hour, now run against a 1 ms tick and a dummy T2 supplied by Buddy 3, with the longest poll call measured by GPIO toggle. Pass: no missed publishes, no resets, dummy-T2 overrun counter zero. Owner: Buddy 1.
A2
The wheel encoders give 20 slots per revolution and the wheels are 65 mm across, so one edge is about 5.1 mm.
Open / Needs validation — now also a connector/phase question
None. The figure came from a typical slotted disc, not the supplied motors.
The kit motors use a six-pin A/B phase connector. If counts per revolution differ, distance (NFR11), turn angle (NFR12) and hump height (NFR13) are wrong together — and the chosen bit widths for the encoder counters and distance fields change with it.
Mark one wheel, roll a measured 1 m by hand, count edges, five times each direction. Publish the measured counts per revolution so every derived figure updates together. Owner: Buddy 2. First bench slot.
A3
Course barcodes are Code 39, single character, delimited by ’*’, 1:3 ratio, 3 mm narrow element derived from the 141 mm symbol length.
Open / Needs validation
None. The 3 mm figure is inferred arithmetic, not a measurement.
If the narrow element is smaller than 3 mm, 1000 Hz no longer gives 10 samples per element and every read fails — silently.
Print the course symbols, measure the narrow element with calipers, confirm the symbology before writing the decoder. Owner: Buddy 3.
A4
The MPU-6050 can be read reliably at 100 Hz over I2C0 at 400 kHz, 14-byte burst under 400 µs.
Open / Converted into a risk — conditional redesign prepared
None. Week 6 assumes an MPU-6050; the kit component list supplies an LSM303DLHC datasheet and the tutor names a GY-511.
The LSM303DLHC has no gyroscope, so the complementary filter and the measured turn rate in FR13 have no source. This is about the wrong device, not an unvalidated number.
Photograph the marking on the physical IMU board (Buddy 5 holds the kit) and post it. If it is the LSM303DLHC, apply the prepared fallback: gated accelerometer-only pitch and kinematic turn rate from T4. Owner: Buddy 4.
A5
HC-SR04 runs from servo port 2 V+ at ~5 V; ECHO divided 10k/20k to 3.33 V stays inside the 3.6 V limit; 70 ms between pings avoids ghost echoes.
Open / Needs validation
Datasheet evidence only (HC-SR04 5 V supply and >60 ms cycle; Robo Pico 3.6 V input limit and servo V+ tied to VIN).
If VIN sags under motor load the sensor drops below 5 V and ranges become unreliable exactly when moving. An undivided 5 V into GP3 would damage the microcontroller.
With the sensor unplugged, feed 5 V into the divider and confirm 3.0–3.6 V. Measure servo port 2 V+ with both motors running. Measure robot width B and length L in the same session. Owner: Buddy 5.
A6
Hump height = Σ sin(pitch) × distance travelled, assuming encoder distance stays valid while climbing.
Open / Accepted as risk
None. Defended by arithmetic in Section 6.3; the tutor ranks it risk 4 of 5.
Wheel slip is most likely on the hump face, exactly where the distance term matters, and the error is silent. If the IMU has no gyro the pitch term also gets noisier.
Hump traverse with encoder distance logged against a tape measure, at 150 and 250 mm/s. Needs A2 closed first. Owner: Buddy 4 with Buddy 2.
A7
Robo Pico Grove ports map to GP0/GP1, GP2/GP3, GP4/GP5, GP6/GP7, GP16/GP17, GP26/GP27 and GP28 for ports 1–7.
Closed — corrected
Robo Pico datasheet Grove table, confirmed by the tutor: Grove 4 is GP16/GP17, Grove 5 is GP6 with GP26, Grove 6 is GP26/GP27, Grove 7 is GP7 with GP28.
None remaining in the mapping itself; the risk moves to executing the rewiring correctly.
Encoder phase A to Grove 4 (GP16/GP17); phase B to GP13 and GP19 as header wires, which belong to no Grove port; GP6 and GP7 left unallocated. Correct A7, the pin table and Figure 1. Owner: Buddy 2 with Buddy 5.
A9
Obstacle width estimable to ±10% by subtracting the 15° beam spread; depth = width; SG90 settles within 50 ms per 30°.
Open / Needs validation
Datasheet evidence only for the 15° angle; no servo timing figure in the kit documentation. A9 was missing from the Week 6 Section 7 table; the tidied version restores it.
Width or depth error breaks the bypass geometry so the car could clip an obstacle (NFR14). Course obstacles are smaller and less smooth than the datasheet’s assumed target.
Scan blocks of 50, 100 and 150 mm at three distances, ten times each; film 30° and 90° servo steps against a protractor. Owner: Buddy 5.
A11 (new)
On the RP2040 (Cortex-M0+) an aligned byte, halfword or word load or store is atomic, and there is no atomic read-modify-write.
Open / Needs validation (documentary)
ARMv6-M architecture reference; no exclusive load/store instructions on M0+. Not yet demonstrated on our build.
If a compiler splits an access to a packed word, or a field straddles a word boundary, the single-writer rule is not sufficient and we would get rare, hard-to-find corruption.
_Static_assert on the size and alignment of every packed shared word; inspect the generated assembly for one representative store; run the packed-data stress test. Owner: Buddy 2.

Constraint Injection / Curveball Response
Injected constraint, recorded exactly as given: “The robot car firmware must minimise the number of bits used to represent application data. Each data field representing application information must use only the number of bits required to represent its valid range, using C bit-fields or explicit masks and shifts where appropriate.” Examples given: a value ranging from 1 to 5 uses 3 bits; a state machine with up to 8 states uses 3 bits; fault conditions such as motor stall, encoder fault, IMU fault, no echo and Wi-Fi loss use individual bits within a shared fault bitmask rather than separate integer variables. It applies to motion control and encoder data, line and barcode sensing, obstacle detection, hump estimation, vehicle and controller states, data shared between tasks or between an ISR and a task, inter-task queue messages, and MQTT telemetry and command payloads. For MQTT, application data should be represented using compact binary fields rather than sending individual values as text. “When multiple values are packed into the same storage unit and that data is shared between tasks, or between an ISR and a task, access must be implemented safely. Read-modify-write operations on shared packed data must not introduce race conditions, and atomic access or appropriate synchronisation must be used where required.” Week 13 evidence required: a data representation table, a RAM usage comparison, a message size comparison, and evidence of no functional loss or unacceptable timing degradation.

Buddy 1
The telemetry record was planned as a text format, which is the opposite of compact binary. FR23’s topic tree, payload schema and command validation were undefined, so there was nothing to shrink. The MQTT STOP path had no flag bit at all.
Defined the full wire format: 20 bytes, explicit shifts and masks, little-endian, version (4 bits) first so the dashboard can reject an unknown layout, then an 8-bit sequence number for loss detection. Commands are exactly one byte: 2 bits of command (START/STOP/RESET/END) and 6 bits of sequence so QoS 1 duplicates are ignored; anything that is not one byte is rejected. Topics fixed as p5is20/car/telemetry (QoS 0), p5is20/car/cmd (QoS 1) and a retained p5is20/car/status with the last will. AI’s suggestion to publish a packed C struct was rejected because bit-field layout is implementation-defined and the dashboard is in Python; half-precision floats and compression were rejected as larger and slower on a core with no FPU. This also closes FR23.

Buddy 2
Every motion and odometry field is affected, and the ISR-to-task encoder path is the most dangerous place to pack. The Cortex-M0+ has no atomic read-modify-write, so naive bit-fields in shared words would be a silent corruption source.
motion_req_t becomes a single uint16_t: 3 bits of command, 12 bits of argument (covering 0–4095 mm, 0–180° and 0–350 mm/s) and 1 source bit — two bytes instead of about twelve, and a message buffer copies it whole, so no sharing question arises. Encoder counters become free-running, one per ISR, each its own storage unit: the ISR only increments (or decrements using phase B), and T4 subtracts the previous value instead of clearing, which removes the clear-race entirely. Authored the three packed access rules the whole team adopted: (1) one writer per packed storage unit, read by an aligned load; (2) any genuinely multi-writer unit goes through a helper that does the read-modify-write in a critical section; (3) nothing an ISR writes shares a storage unit with task-written data. Scope decision defended and recorded: packing applies to data that is stored, shared or transmitted; arithmetic intermediates such as PID integrators and filter accumulators keep native width, listed as a justified deviation.

Buddy 3
Three ADC channels, the line error, the decoder state and a 29-element capture buffer — the capture buffer is the largest array in the firmware and sits in the 1 ms loop, which is the worst place to add masks and shifts.
Element durations stored as uint8_t milliseconds, saturating at 255: the longest valid wide element at the slowest speed in NFR8 (100 mm/s) is about 90 ms, so anything that saturates is out of range and already rejected — 29 bytes instead of 58, with no shifting in the tight loop. Line error quantised to 8 bits signed (±127 for a normalised ±1, about 0.8% of span) and packed with the 2-bit line state and junction/end flags into one 16-bit word, written by T2 alone. Last barcode (none/A/B/C/D) is 3 bits — the requirement’s own “1 to 5” example — and the reject reason 3 bits. Accepted the quantisation as an assumption to be checked: the raw ADC difference will be logged beside the 8-bit value on the first track run, and the field widens to 10 bits if it is not enough.

Buddy 4
Pitch, turn rate, motion class, hump height and the whole fault story. The requirement’s named “shared fault bitmask” is the same artefact as the consolidated fault table the tutor asked for.
One uint8_t fault mask, one bit per fault, and the fault table in this document has one row per bit: bit 0 E-STOP request, 1 motor stall, 2 encoder fault, 3 IMU fault, 4 impact, 5 no echo, 6 bypass failed, 7 WiFi loss. A compile-time FAULT_CRITICAL_MASK excludes WiFi loss so NFR19 still holds — losing the network must not stop the car — while no-echo was argued up to critical because driving blind into an obstacle is worse than stopping. Because four tasks and an ISR write it, access is only through interrupt-masked helpers. flg_sys keeps a single summary ESTOP bit rather than eight fault bits, so T6 is not woken by conditions that belong to T1. Final Tribunal Summary
Final question
Team answer
What is the strongest part of the current design?
The ownership discipline. Every device, every kernel object and now every packed storage unit has exactly one named owner, with exactly one documented exception — T1 forcing the motor PWM off — and that exception is drawn in red, justified, and now guarded on both sides. It is what lets a seven-task system run on one mutex, and it is the reason the change requirement cost us a set of rules rather than a redesign: “one writer per word” is the same idea as “one owner per device”. The tutor review endorsed the small kernel-object set, and nothing in today’s discussion needed a new object.
What is most likely to fail?
The hardware facts the arithmetic rests on, with A2 first. Counts per revolution is the single number that distance (NFR11), turn angle (NFR12), hump height (NFR13), the bypass geometry, the end-of-course distance threshold and several bit widths all inherit, and it was taken from a generic slotted disc rather than the supplied motors. Close behind is the IMU part: if the kit board is an LSM303DLHC, the complementary filter and the measured turn rate in FR13 have no source and Figure 6 is redesigned, not retuned. Both failure modes are silent — a wrong scale factor and a missing gyro both look like a tuning problem for a week before anyone checks the number.
What evidence supports readiness?
Interface-level: every subsystem has a provider, named consumers, a written interface rule and a validation rule, and after today every task and ISR has an owner. Analytical: the utilisation argument (≈18.9% against a 72.9% bound) stands unchallenged on arithmetic, and the Code 39 element geometry is derived rather than assumed. Procedural: eight integration risks with owners, seven cross-subsystem tests of which three are timing, safety or shared-resource tests, and a cr1-baseline tag cut before any packing lands so the Week 13 comparisons are measurable. What we do not have is measured evidence on hardware, and we have said so in every row rather than rounding it up.
What did AI miss that human discussion revealed?
Three things, all of which came out of buddies arguing with each other rather than with a tool. First, that the six-pin kit connector implies A and B phases, so correcting the Grove mapping was necessary but not sufficient — a point raised only when Buddy 3 challenged Buddy 2’s two-GPIO plan. Second, that flushing mbf_motion at the handover is itself racy, which Buddy 2 spotted in Buddy 5’s accepted fix and which produced the source-bit solution. Third, the scope boundary for the change requirement: no tool told us that packing PID integrators and filter accumulators saves nothing and costs time, because that judgement depends on knowing which variables live on a task stack and never leave it. AI also proposed a packed C struct for the MQTT wire format, which would have failed silently against a Python dashboard.
What did AI correctly identify after discussion?
The tutor review and our pre-Zoom AI work were right about every structural hole we then confirmed: the T1-to-T4 override window, the single GPIO callback per core, the 1 ms kernel tick and the absent drift-free release for T2, the barcode command being applied at the barcode rather than the junction, the all-black end marker colliding with L2 JUNCTION, the unflushed mbf_motion, and the undefined MQTT schema that left FR23 untestable. Each of those turned into a decision in the change log rather than a wording fix. The final AI-vetted pass then found three things we had genuinely missed: the obstacle profile does not fit the single-writer rule we had just adopted, an exactly-full eight-bit fault mask has no room to grow, and our E-stop test could pass while the race it was meant to catch still fired.
